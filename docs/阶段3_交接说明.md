## 2. 阶段 3 做了什么

### 2.1 写入链路

```
load_context ──→ extract_memories ──→ merge_memories ──→ commit_memory
                                                          │
                              ┌───────────────────────────┘
                              ▼
                     parse_parent_input（chat）
                     next_step（feedback）
```

**顺序是硬要求**：抽取必须在解析之前。`parse_parent_input` 会把上一轮累积的
`observed_facts` 并进 `case_summary`；先解析的话，家长这一轮刚纠正的旧值
已经混进本轮事实了，再标作废也来不及。

### 2.2 四层记忆落在哪

| 层 | 内容 | 存储 |
|---|---|---|
| L1 稳定档案 | 事实 / 偏好 | `children.confirmed_facts_json`（对象数组，兼容旧字符串） |
| L2 情境观察 | 一次具体发生的事 | `observations`（结构化字段 + `source_quote`） |
| L3 待验证假设 | 对重复模式的暂定解释 | `hypotheses`，状态默认 `candidate` |
| L4 干预尝试 | 系统给过、家长选过的方案 | `trials`（记忆层只读） |

### 2.3 判定规则（`rdi_agent/memory/merge.py`）

纯函数，不连库不调模型。核心立场：**代码只能把模型的判断降级**。

```
auto_commit  <  needs_confirmation  <  discard
                          ↑
                  取 max(模型建议, 规则下限)
```

唯一的**升级例外**：家长明确纠正旧事实（有效 `replaces_memory_id` +
逐字原话 + `inference=false`）。没有这个例外，"纠正后不再沿用旧值"
会永远被保守的模型卡住。

### 2.4 幂等

| 场景 | 靠什么 |
|---|---|
| 同一次请求重放 | `memory_events` 唯一索引 `(child_id, conversation_id, turn_id, content_hash)` |
| 追问恢复重复抽取 | 内容哈希去重（跨 turn）+ 观察/假设的部分唯一索引 |
| 事实 JSON 并发写 | `SELECT ... FOR UPDATE` 锁 `children` 行 |
| 纠正重发 | 同内容哈希的活记忆直接返回 |

### 2.5 管理接口

| 方法 | 路径 |
|---|---|
| GET | `/api/children/{child_id}/memories?family_id=...` |
| POST | `/api/children/{child_id}/memories/{memory_id}/confirm` |
| PATCH | `/api/children/{child_id}/memories/{memory_id}` |
| POST | `/api/children/{child_id}/memories/{memory_id}/delete` |

记忆 id 用前缀路由到不同的表：

```
fact_<hash16>      children.confirmed_facts_json
pref_<hash16>      children.confirmed_facts_json（偏好）
obs_<uuidhex>      observations
hyp_<uuidhex>      hypotheses
attempt_<uuidhex>  trials（只读）
```

### 2.6 前端

`frontend_rdi/src/components/MemoryPanel.vue`，挂在右栏证据面板上方：

- 按 事实 / 偏好 / 观察 / 假设 / 尝试 分组
- 每条显示状态、原话、来源轮次、取代/反例链接
- 待确认的可以直接"确认"；都能"纠正"（行内编辑）和"删除"
- 顶部 "同一孩子新会话" 按钮 —— 验收第 1 条靠它演示

## 3. 当时要决定的几件事（结论）

### 3.1 事实要不要单独一张表？

**不建。** 计划 §10.2 把 L1 放在 `children` 上，阶段 3 照做。
代价是 JSONB 数组没有数据库级唯一约束，只能靠行锁 + 应用层去重。
条数上限 50，够用。真到了需要强约束那天，再拆 `memory_facts` 表。

### 3.2 抽取放解析前还是后？

**放前面。** 见 §2.1。这是本阶段最容易被做反的一处。

### 3.3 反馈入口这一轮接不接？

**接。** 计划 §10.3 的流程图写的是"用户输入 / 执行反馈"。
阶段 4 只负责"反馈分析 + 下一步"，不用再改图拓扑。

### 3.4 模型说"可以自动记"，代码要不要照做？

**不照做。** 代码只降级不升级（一个纠正例外）。
理由：记错一条事实，之后每一轮都会拿它当背景；
多问家长一句的代价小得多。

### 3.5 反例怎么削弱假设？

由模型给 `contradicts_memory_ids`（必须从 prompt 里给的假设 id 原样抄），
代码校验 id 存在后：状态 → `weakened`、置信度降一档、
反例 id 追加进 `contradicting_observation_ids_json`。
**同一条观察又说一遍但带来了新反例**时，不丢，走 `link_contradiction`。

## 4. 下一个阶段会撞上的问题

1. **`case_summary` 里可能残留旧事实**。作废清单只过滤"旧内容是新内容的
   全部或一部分"的情况；模型把旧值改写成同义句时，过滤不掉。
   下一轮 `load_context` 不会带进来，风险主要在同一 thread 的 checkpoint 里。
2. **冲突检测依赖模型**。模型没给出 `replaces_memory_id`，纠正就不会生效。
   prompt 里写死了规则，但做不到 100%。人工验收时留意这条。
3. **同一天重复报告同一件事会被去重掉**。内容哈希不看日期；
   如果"频率"本身是信息（一周哭了五次），阶段 4 要考虑把时间加进哈希。
4. **`memory_events` 里没有真正的"删除内容"**。`before_json` 存的是
   删除前的整条记录 —— 满足审计，但如果将来要求"彻底忘记"，要额外处理。
5. **没有真正的访问控制**。接口靠 `family_id` 校验归属，不是鉴权。阶段 5 再说。

## 5. 硬约束（别踩）

| 约束 | 说明 |
|---|---|
| 抽取一律 `json_schema` | `llm.chat_json(model_cls=...)`，不许 `json_object` |
| 记忆失败必须降级 | 节点接住所有异常，只留 note，不能阻断回答 |
| 作废清单不进 prompt | `memory_forbidden_facts` 只给代码过滤用 |
| 模型推断不能成为事实 | `inference=true` 一律转 hypothesis（`candidate`） |
| 改中文文件用 ASCII 锚点 | Edit 的 `old_string` 含中文时匹配不可靠 |
| 不动 `legacy/` | 旧实现只读 |
| 不自动跑浏览器全流程 | 用户自己手动测；这边只验接口和测试 |
