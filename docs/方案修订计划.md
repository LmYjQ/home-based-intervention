# 方案修订计划（把 Time Travel 引入家长正常流程）

> 状态：待实现
> 起草：2026-10-26
> 关联：`langgraph_family_assistant_phased_plan.md` §11（阶段 4 反馈迭代）、§12（阶段 5 持久化与调试）

---

## 1. 要解决的问题

家长执行了一周方案，回填反馈时才发现"情况有变"——比如原本计划早上送园，但最近只有晚上有时间；或者原本以为孩子怕的是分离，现在发现怕的是声音。

现在的处理方式只有两种，都不解决问题：

- 家长重新开一段对话，重新描述一遍情况——**前面已经问清楚的、已经找到的指南依据全部作废**，而且家长要重新回答同样的问题。
- 接受现有方案，不做调整——家长看到的是一份"不贴合当前情况"的建议。

**目标**：家长在反馈环节补充新情况后，能基于**已经问清的、已经取到的依据**，只重做"生成建议卡"这一步，拿到一版贴合新情况的卡。

这就是把 Time Travel（从历史 checkpoint 派生新分支）从调试工具变成产品能力。

---

## 2. 家长看到什么

```
家长选定方案 v1  →  执行一周  →  填完反馈  →  看到反馈结果
                                                    │
                                          ┌─────────────────────────┐
                                          │ 情况有变？重新出一版方案  │
                                          │ [补充新情况____________]  │
                                          │      [ 重新生成方案 ]      │
                                          └─────────────────────────┘
                                                    │
                                          方案 v2（2–3 张卡，标注"第 2 版"）
                                                    │
                                          家长选一张  →  新的一次尝试
```

三条产品规则：

1. **不重新问家长**。上一轮问过什么、家长答了什么，全部沿用。家长刚答完又被问一遍，是最伤体验的事。
2. **不重新查指南**。上一轮找到的证据包沿用，新卡继续引用同一批依据。家长要的是"换个做法"，不是"换一批依据"。
3. **旧版本保留**。v1 的卡和 v1 的那次尝试都不删，在界面上标成"已归档"，家长能看到第 1 版和第 2 版的差别。

## 3. 回溯点：为什么选在"生成建议卡"之前

整条链路的业务结构是：

```
理解（问清了什么）─┐
取证（找到什么依据）─┼─→ 生成建议卡 ─→ 安全审查 ─→ 渲染 ─→ 落库 ─→ 让家长选
门控（证据够不够）──┘
```

分界线在**生成建议卡**这里：

- 分界线**左边**是这一轮的**输入**：已知的事实、已找到的依据、门控结论。重新生成不改变这些——家长补充的信息是"加入"事实，不是"推翻"依据。
- 分界线**右边**是这一步的**产物**：建议卡、审查结果、渲染文本、要落库和要选的卡。重新生成就是重做这些。

所以回溯点定在"生成建议卡"这个节点之前，落在这个位置上的历史状态（checkpoint）作为分叉起点。

**为什么不选更靠前的位置**：

- 选在"理解"之前 → 充分性判断会重跑。上一轮如果没问满 2 轮，模型可能又要求补充信息，家长刚答完又被问一遍。
- 选在"取证"之前 → 整条检索链重跑（向量检索 + 重排 + 外部 API），慢且花钱，而且新查出来的依据未必比原来的好。

**副作用位置也支持这个切法**：分界线左边有写库动作（记忆写入、证据包落库），分界线右边的写操作（候选卡落库、选定建尝试）都是**幂等**的——按卡号或"已有有效尝试"判重，重跑不会产生重复数据。

## 4. 重新跑什么 / 复用什么

### 4.1 重新跑（图内自动跑）

| 环节 | 干什么 | 备注 |
|---|---|---|
| 生成建议卡 | 用合并后的事实 + 同一包证据重新出 2–3 张卡 | 全流程最慢的一步 |
| 安全审查 | 规则闸 + 模型复核，逐卡检查 | 新卡必须重新过闸 |
| 渲染 | 拼出给家长看的正文 | 纯规则，不调模型 |
| 候选卡落库 | 新版本卡入库，状态"待选" | 幂等 |
| 等待家长选 | 停在选卡这一步 | |
| 选定建尝试 | 家长选完，新建一次尝试 | 幂等 |

### 4.2 复用（完全不重跑）

| 环节 | 省下的东西 |
|---|---|
| 装载记忆上下文 | 直接沿用 |
| 充分性判断 / 生成追问 / 等待回答 | **家长不会被重新问一遍** |
| 查询改写 / 知识检索 / 重排 / 父块扩展 | 不重新检索，不重新排序，不花向量和外部 API 的钱 |
| 证据包落库 | 新卡挂同一个证据包，依据可追溯 |
| 证据门控 | 门控结论沿用 |

### 4.3 成本对比

- 沿用证据：约 4 次模型调用，0 次检索
- 完全重跑：约 6–7 次模型调用 + 1 次向量检索 + 1 次外部重排

## 5. 三条必须配套的规则

不做这三条，流程会静默出错。

### 5.1 新信息要并进"已知事实"，不能靠图自动跑

"把家长的话并进事实清单"这个动作在图里排在充分性判断之前。要让图自动跑它，回溯点就得再往前挪，那家长就会被重新问一遍。

**做法**：在接口层直接复用现成的事实合并逻辑（纯函数、不碰数据库），把新信息通过"家长补充"通道塞进去——这条通道是**代码兜底**的，不依赖模型抽取，保证新信息一定进事实清单。同时把"已作废事实"清单一并传进去，保留原有的过滤行为。

**结果**：新事实和旧事实合并，旧事实一条不丢，已删除/已纠正的旧事实照旧被过滤。

### 5.2 新信息里的风险信号必须复查

证据门控不重跑，就意味着家长补充"孩子最近开始打人"这类**新出现的风险**不会被发现。

**做法**：在接口层补一次纯规则的强制判定（不调模型，零成本）。命中风险就走"建议找专业人士"的分支，不出卡。

**为什么不用改图**：门控的路由函数读的是状态里的"门控结论"字段，把强制判定结果写进这个字段，路由会自动改道。新卡本来就要重新过安全审查，这条规则不需要额外的图结构改动。

### 5.3 卡号必须带版本前缀

候选卡落库时按"会话 + 卡号"判重。模型出的卡号是写死的 `plan_1 / plan_2 / plan_3`，重新生成的卡会撞上旧卡——**新卡根本不会落库，家长"选"的是旧卡**。

**做法**：卡号加版本前缀（第 1 版保持原样以兼容已有数据，第 2 版起加 `r2_` 前缀），前缀要在生成提示里就告诉模型，保证卡内交叉引用一致。

## 6. 数据与接口

### 6.1 需要记下来的东西

为了让"从哪一版分叉"这件事可追溯，方案卡要额外记住两件事：**产生它的那一轮**、**分叉起点那个 checkpoint 的 id**。

（第一版可以先不加这两列，用"会话历史里最后一个待生成检查点"兜底定位；但多轮会话下可能定位错，建议加列。）

### 6.2 新增接口

```
POST /api/trials/{trial_id}/revise
{
  "revision_note": "家里没人帮忙接送，只能晚上做",   // 必填，家长补充的新情况
  "turn_id": "turn_rev_..."                          // 幂等键
}
```

返回沿用现有选卡接口的形状：状态、候选卡列表、版本号、复用了哪些环节。

家长选完卡，**复用现有的选卡接口**——分叉落在同一条会话线程上，选卡中断是同一个，不需要新接口。

### 6.3 幂等

`turn_id` 是修订的幂等键：重复提交同一个 `turn_id` 不产生第二条分支、不重复落库。

## 7. 前端

反馈结果卡下面加一块：

- 标题"情况有变？重新出一版方案"
- 一个输入框，家长补充新情况
- 一个"重新生成方案"按钮（请求中置灰，防连点）

返回新卡后，方案列表按版本分组展示：

- 第 2 版：当前版本，可选
- 第 1 版：已归档，灰显，保留可查

选完新卡后，"记录这轮尝试的反馈"指向新的那次尝试；旧的那次尝试和它的反馈仍在历史里。

调试面板（checkpoint 列表）不用改——分叉后线程历史里自然会出现分支，调试面板已经能列出，顺带成了"时间旅行"的可视化。

## 8. 分期

**第一期（做这些）**

- 回溯点定位 + 同线程分叉
- 事实合并（接口层复用）
- 风险信号复查
- 卡号版本前缀
- 新接口 + 前端入口 + 版本分组展示
- 幂等

**第二期（以后再说）**

- **重查证据**档位：家长新情况影响很大时，检索链也重跑一遍。机制一样，只是回溯点再往前挪一格。
- **新信息写进长期记忆**：第一版不做——同线程分叉后事实清单留在修订版的会话状态里，下一轮会继承，约束不会丢。记忆是跨场景的额外层，牵扯"自动记 / 待确认 / 丢掉"三态判定，先不动。

---

## 9. 验收标准

- [ ] 家长在反馈环节补充新情况，能拿到一版新卡
- [ ] 过程中家长**没有**被重新提问
- [ ] 新卡引用的是**上一版同一批**指南依据（证据包 id 相同）
- [ ] 家长补充"孩子最近有攻击行为"时，**不出卡**，改走专业支持话术
- [ ] 新卡和旧卡卡号不撞车；选新卡不会选到旧卡
- [ ] 选完新卡建的是**新的一次尝试**，旧尝试和旧反馈都还在
- [ ] 同一个 `turn_id` 提交两次，只产生一条分支
- [ ] 旧版本卡在界面上标为"已归档"，可查看

## 10. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 沿用的证据与新情况不匹配 | 证据讲的是早接送，新情况是晚接送 | 卡的生成提示里明确告诉模型"这一版沿用了上一版的依据"；第二期提供重查档位 |
| 定位到错误的回溯点 | 多轮会话下"最后一个待生成检查点"可能不是这一轮的 | 加列记 `分叉起点 checkpoint id` |
| 重复分叉 | 家长连点两次 | `turn_id` 幂等 + 按钮置灰 |
| 版本链混乱 | v1→v2→v3 反复分叉 | 每次从上一版的分叉点分叉，形成一条链，不互相覆盖 |
| 与阶段 4 既有决定冲突 | 计划 §11.4 现在写着"调整只出文字，不出新卡" | 本文即是对它的放开，需同步改写 §11.4 并新增 §11.7 |
