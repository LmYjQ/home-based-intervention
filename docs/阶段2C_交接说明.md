### 2.3 引用校验（**必须实现**，计划 §9.3 验收点）

逐条检查 `RecommendationCard.source_citations` 里的每一条：

1. `citation.source_id` 必须能在当前 `EvidenceBundle` 的 `evidence_id` 里找到
   —— 找不到就是**编造引用**
2. 章节和页码必须与对应的 `EvidenceItem` 一致
3. `application_label == "source_summary"` 时必须至少有一条引用

任何一条失败：**带错误信息重试一次**；仍失败则**丢弃该卡**，
降级为 `limited_answer`，并在 trace 里记 `citation_validation_failed`。

> **字段语义的坑**：计划 §5.5 说"每一条 `source_citations` 必须能在
> 当前 `EvidenceBundle` 中找到对应 `evidence_id`"，而校验清单写的是
> "`citation.source_id` 是否存在"。
> **实现约定：`SourceCitation.source_id` 里放的是 `evidence_id`（chunk 的 UUID）**，
> 不是 `knowledge_sources.source_id`（`guideline2026`）。
> 这样校验才能精确到"页码对不对得上"。
> 写 prompt 时要明确告诉模型这一点，否则它会填 `guideline2026`。

## 3. 当时要决定的几件事（都已定，结论附在各小节末尾）

### 3.1 `retrieval.py` 怎么拆

现在 `retrieve()` 是一个大函数（改写 → 双路 → RRF → 重排 → 父块扩展 → 证据）。

图里要拆成 `retrieve_knowledge` 和 `rerank_and_expand` 两个节点，
**建议拆成三个可单测的公共函数**：

```python
recall_candidates(queries, candidate_k, use_vector) -> (vector_cands, fts_cands, merged)
build_evidence_bundle(candidates, queries, ...) -> EvidenceBundle
```

`retrieve()` 保持为"三步串起来"的便捷入口（评测脚本在用，别删）。

> **已定的结论**：拆成 `recall_candidates()` + `build_evidence_bundle()`，
> 两个函数都在 `rdi_agent/rag/retrieval.py` 里，`retrieve()` 保留为便捷入口。
> `recall_candidates()` 返回 `RecallOutcome`（三路候选 + notes），
> 因为图里 `retrieve_knowledge` 节点要往 state 里放**精简**候选，
> 不能放完整候选对象 —— 见下一段。

**注意 `retrieval_candidates` 放什么**：计划 §4.2 说
"原文片段只放 `evidence_id` 或摘要，避免 State 膨胀和日志泄露儿童信息"。
所以 `state["retrieval_candidates"]` 应该是**精简的**候选列表
（chunk_id + score + 页码 + 一小段摘要），不是完整候选对象。

> **已定的结论**：`retrieve_knowledge` 节点只往 state 放
> `{"chunk_id", "score", "section_code", "pdf_page_start", "pdf_page_end", "snippet"}`；
> `rerank_and_expand` 节点要全文时，用
> `rag/search.py::load_candidates_by_ids()` **按 id 回库取**。
> 这么绕是有意的：既不撑爆 State，也不违反"state 里不放原文"的约束
> （计划 §4.2）。

### 3.2 `rewrite_query` 节点的查询怎么来

`query_rewrite.rewrite_query()` 现在接受**一个字符串**。
但图的输入是 `case_summary`（结构化）。

`CaseSummary` 的字段：`observed_facts` / `parent_goals` / `context` /
`already_tried` / `missing_information` / `retrieval_concepts` / `risk_signals`。

**待定**：怎么从这些字段拼出检索查询？
建议：优先用 `retrieval_concepts`（已经是抽取出的概念线索），
不够时用 `observed_facts` 拼。**但要注意计划 §5.4 的约束**：

> 查询改写只能使用**已确认事实**，不能把待验证假设写进检索词，
> 否则会把假设当成事实检索。

`retrieval_concepts` 是"线索"，不是事实 —— 这个边界要想清楚。
（`CaseSummary` 没有区分"已确认"和"待验证"的字段，可能需要看
`tentative_interpretations` 之类的结构，或者在 prompt 层面约束。）

> **已定的结论**：查询由 **`observed_facts` + `parent_goals`** 拼成
> （不是 `retrieval_concepts` —— 那是线索不是事实，用它会把假设当事实检索）。
> `retrieval_concepts` 走**术语桥接**那条路（`rag/query_rewrite.py`），
> 桥接的词要过 `is_explicit_in_source` 过滤 ——
> 知识库里根本不存在的词不许进检索词。
> 节点实现见 `rdi_agent/graph/nodes/retrieval_nodes.py::rewrite_query`。

### 3.4 证据门控怎么判

计划 §5.5 给了五条路径：

| 条件 | `evidence_status` | 路由 |
|---|---|---|
| 有直接相关且定位准确的证据 | `direct` | `recommend` |
| 只有间接相关证据 | `indirect` | `limited_answer` |
| 检索结果互相矛盾 | `conflicting` | `limited_answer` |
| 没有可靠证据 | `none` | `limited_answer` |
| 缺失信息会改变建议 | `none/indirect` + `needs_followup` | `followup` |

**建议规则优先**（能纯规则判的不调 LLM）：
- 证据包为空 → `none` / `limited_answer`
- 有证据但 `relevance_reason` 全是"仅向量召回"、术语桥接为 0、且重排降级
  → 可能是 `indirect`
- 其余交给 LLM 判 `direct` / `indirect` / `conflicting`

**但 2B 量出过一个大问题**（`evals/REPORT_v1.md` §5.1）：
**无关问题也会召回 5 条证据**（硬凑率 100%）。所以
"证据包非空"**不能**直接当成"有证据"——
门控如果只判空不判质量，2C 就会把噪声当依据给家长。

> **这一条在中文指南这一版已经修掉了**（`evals/REPORT_v3.md` §2）：
> 硬凑率 **0%**（3 条无关题一条都没硬凑）。做法是给向量路加相似度下限
> （`MAX_VECTOR_DISTANCE = 0.52`）—— 中文 bge-m3 上相关查询最近邻距离
> 0.2876–0.4691、无关查询 0.5675–0.6071，0.52 是分界。
> **但门控仍然要判质量，不能只判空** —— 阈值是标定出来的，不是保证。

> **已定的结论**（`rdi_agent/graph/evidence_gate.py`）：
> **规则优先，LLM 为辅**。三条写死在代码里，LLM 说什么都不能推翻：
>
> 1. 家长报了严重风险信号 → `risk` / `high_risk` / `professional_support`（**不调 LLM**）
> 2. 证据包为空 → `none` / `limited_answer`（**不调 LLM**）
> 3. 没有任何证据达到采信门槛 → `can_support_personalized_advice=False`，
>    `direct` 降 `indirect`，`recommend` 降 `limited_answer`
>
> 「达到采信门槛」的判据是 `usable_evidence()`：
> **关键词路命中过**，**或**向量距离 ≤ `DIRECT_MAX_DISTANCE`（0.50）。
> 三层距离门槛从宽到严：`MAX_VECTOR_DISTANCE`（召回，0.52）
> → `STRICT_VECTOR_DISTANCE`（合并，0.52）
> → `DIRECT_MAX_DISTANCE`（采信，0.50）。

`send_message` / `select_plan` 用的是**普通 dict** 调 `graph.ainvoke(...)`：

```python
await graph.ainvoke({"user_message": msg, ...}, config=config)   # ❌
```

LangGraph 里，**普通 dict 不会恢复 `interrupt()`**，它会让图**从 START 重跑一整条链**。
后果有三个：

1. `await_user_answer` 节点永远跑不完 → 每轮都是一个新开的中断
2. `followup_rounds` 永远是 `None` → `MAX_FOLLOWUP_ROUNDS = 3` 那个兜底**形同虚设**，
   模型可以无限追问
3. `present_plans` 的中断没被恢复 → 它后面的 `commit_plan_selection` 根本不执行
   → **trial 建不出来**

### 修法

按"当前 thread 停在哪个中断上"分流，停下时用 `Command(resume=...)`：

```python
pending = await _pending_interrupt(config)     # 读 aget_state().tasks 里的 interrupts

if pending and pending.get("kind") == "followup":
    result = await graph.ainvoke(
        Command(resume=req.message, update={"turn_id": turn_id}), config=config)
else:
    result = await graph.ainvoke({...普通 state...}, config=config)   # 新开一轮
```

`select_plan` 同理，用 `Command(resume={"plan_id": ...})` 恢复方案选择中断。

> `Command(update=...)` 里的 `turn_id` 是必要的：恢复时节点会重跑，
> 不显式带上就会用旧的 turn_id，幂等判断会串。

### 为什么之前没被测出来

`tests/test_graph_flow.py` 是**直接调图**、用 `Command(resume=...)` 恢复的 ——
它测的是图，测不到 API 层。**图是对的，API 是错的**，所以全部单测都绿。

新增 `tests/test_api_conversation_flow.py`：从 API 入口走一遍，
断言 `followup_rounds` 真的递增、**只问一轮**的兜底真的强制收手、`trial` 真的落库。
（改了 API 的中断恢复方式，**必须**跑这个文件。）

### 对 2C 的影响

2C 要在图里加 `evidence_gate` 等节点，**接口层也要跟着改**：
新增的 `safety_review` / `render_answer` 如果也要中断，
`rdi_agent/api/conversations.py` 的 `_pending_interrupt` 分流要一起扩。

### 4.6.1 顺带修掉的一个 500：`recommended` 漏写

**症状**：生成建议卡那步 500，日志是

```
LLMError: build_recommendation 连续 3 次 schema 不合规：plans(value_error)
```

**根因**：`RecommendationCard.recommended` 在 pydantic 上有默认值 `False`，
所以它**不在** json_schema 的 `required` 列表里 —— 结构化输出允许模型整张卡
都不写这个字段。漏写之后三张卡全是 `False`，
`RecommendationSet` 的「必须恰好一张卡 recommended=True」校验就抛错。
实测**大约三次里撞上一次**（第一次跑完整流程就撞上了）。

**修法**（两层）：

1. `RecommendationCard` 加 `json_schema_extra` 钩子，把 `recommended`
   塞进 json_schema 的 `required` —— **从协议层堵住漏写**。
   pydantic 侧保留默认值，只让**模型**必须显式表态，
   代码构造这张卡时不用每次都写。
2. `build_recommendation` 节点 catch `LLMError`，降级为 `limited_answer`
   而不是让整个请求 500。计划 §9.3 的原意是「生成不出来就给有限回答」，
   不是「整个请求挂掉」。家长拿到一句有限回答，比拿到一个 500 强。

> **没有动 `RecommendationSet` 的严格校验**。
> `tests/test_conversation_schemas.py` 里
> `test_recommendation_set_rejects_zero_recommended` 编码的是有意的契约
> （"一张都不推荐等于把活推回去"），放宽它等于把这个设计意图扔了。
> 新增的回归测试 `test_recommended_is_required_in_json_schema` 断言的是
> **json_schema 的 required 列表**里有这个字段。

### 4.6.4 同一个 bug 的第二个实例：`source_citations` 漏写

**症状**：不报错，但家长答完这轮追问后拿不到任何建议卡，
只拿到一段没有出处的文字。日志是

```
LLMError: build_recommendation 连续 3 次 schema 不合规：
plans.0(value_error); plans.1(value_error); plans.2(value_error)
```

**根因**：和 `recommended` 完全同一类 —— `source_citations` 有默认值 []，
不在 json_schema 的 required 里，模型可以整张卡都不写它。
模型把 `application_label` 填成 `source_summary`（"这是指南里说的"）却不给引用，
`source_summary_needs_citation` 校验器就抛错，**三张卡一起废掉**。

**修法**：同样加 json_schema 钩子把 `source_citations` 塞进 required。
要求"字段必须出现"不等于"必须有引用" —— 空数组是合法答案。

**顺带修的**：这种退化原本会被报成 `completed` ——
`evidence_decision` 说的是 `recommend`（证据是够的），
只看它就以为流程正常跑完了。现在 `_status_of` 也看 `answer_mode`，
走到有限回答这一路就报 `limited_answer`。

> **教训**：这类「有默认值 → 不在 required → 模型省略」的坑，
> 在这个仓库已经出现**三次**了（`options` / `recommended` / `source_citations`）。
> 写新契约时，**每个有默认值的字段都要确认它进了 json_schema 的 required**，
> 否则模型有权省略它。

### 4.6.5 流式进度（方案 A：流进度，不流半截答案）

**要解决的**：家长点「发送」后要等 30–90 秒（模型侧延迟实测 2.8s–55s），
中间只有一个转圈 —— 家长不知道系统在干什么，以为坏了。

**为什么不做流式输出**：抽取类调用一律走 `json_schema` 严格约束解码
（仓库铁律，见 `rdi_agent/llm.py`）。结构化输出下模型必须保证 JSON
语法合法才能吐 token，吐出来的是 `{"plan_id": "pl` 这种半截 ——
浏览器端没法用，家长也看不懂。

而且这一轮跑的是 `parse_parent_input` / `generate_followup` /
`build_recommendation` 这类**结构化抽取**，产物是契约对象，
不是给家长看的回复文案。

**所以流的是"步骤进度"，不是答案本身**：

```
正在理解你说的情况 → 正在判断信息够不够 → 正在检索指南 → 正在整理建议
```

**实现**：

| 文件 | 改动 |
|---|---|
| `rdi_agent/progress.py` | 新增。进度事件总线。`ContextVar` 按 task 隔离 —— 并发请求不串事件 |
| `rdi_agent/llm.py` | 接上**一直是空钩子**的 `on_step`（`llm.py:257`）。10 个调用点自动吃到，不用逐个改 |
| `rdi_agent/graph/nodes/retrieval_nodes.py` | 补 `rewrite_query` / `retrieve` / `rerank` / `evidence_gate` / `safety_review` / `render` 六个点（这些节点不调 LLM 或走了规则分支，`chat_json` 的钩子抓不到） |
| `rdi_agent/graph/nodes/chat_nodes.py` | 补 `await_answer` / `present_plans` 两个点 |
| `rdi_agent/api/conversations.py` | 新增 `POST /messages/stream`（SSE）。`_run_turn` 抽出来，流式/非流式**共用同一套逻辑** |
| `frontend_rdi/src/api.js` | `streamMessage()` —— fetch + ReadableStream 自己解 SSE 帧（EventSource 只支持 GET 且不能带 body） |
| `frontend_rdi/src/App.vue` | 进度条 UI |
| `tests/test_api_stream_flow.py` | 新增。8 个用例 |

**关键设计**：进度接在 `llm.chat_json` 这个**唯一出口**上 ——
所以新增一个抽取节点，**不用改代码就自动有进度**。

> **踩过的坑**：同一个阶段既手动 `progress.emit` 又走 `chat_json`，
> 会推两条重复事件。要么只手动打（规则分支走的），要么只靠 `chat_json`
> （LLM 分支走的），不能都要。

> **阶段数不是固定的** —— 取决于图走到哪。只发第一句就只看到 4 个
> （图停在追问中断上，检索链根本没跑）。答完一轮追问才看得到完整的 11 个。

**为什么流式和非流式必须共用逻辑**：手测台的价值就在于"看到的就是真的"。
两条路跑不同逻辑的话，手测看到的东西不能代表线上。
`test_stream_result_matches_non_streaming` 这个用例就是钉这条的。

### 4.6.6 知识库引用的显示逻辑

**症状**：左右两边都有东西，但**对不上号** ——
左边卡上写「引用（空）」，右边却有 8 条证据。

**根因**是三个独立的问题叠在一起：

**1. `GET` 返回的方案卡是摘要，不是整张卡**

`list_plans` 只返回 `plan_id` / `title` / `status` / `recommended` /
`application_label` 五个字段，**整张卡的内容（`plan_json`）没返回**。
前端把这份摘要直接喂给 `PlanCard` 渲染 —— 卡上只剩标题，
引用、家长可以做的事、观察指标全没了，看起来像"引用被清空"。

**修法**：`list_plans` 返回整张卡。另外停在选方案中断时，
`GET` 优先返回**中断里那份候选卡** —— 那才是"当时给家长看的那三张"
（落库那份的 `status` / `recommended` 是后来改的）。

**2. 引用和证据分属两个组件，谁也不认识谁**

引用里的 `source_id` 填的就是证据的 `evidence_id`
（约定见 `rdi_agent/prompts/chat.py` 的 `_CITATION_CONTRACT`）——
卡上的引用和右边的证据**说的是同一段东西**。

但分开看就是两堆对不上的文字：家长只能自己在两堆 UUID 里找同一个。
现在前端做了 join：

- 卡上的**章节和页码取自证据**（不取引用上模型填的那些 —— 模型经常填 `null`）
- 「见右侧证据第 N 条」里的 N 是证据面板里的序号
- 右边被引用到的证据打「已引用」徽章 + 蓝色描边
- 引用在证据里找不到时，卡上明写「⚠ 没在本次证据里找到这一条」

**3. 顺带修的**：Vue 侧踩了个 `Maximum recursive updates exceeded` ——
`citedIds` 每次都赋一个新数组 → 重渲染 → 组件 ref 回调 → 再赋值，无限递归。
加了个比对才停住。

计划 §9.2 最后一条任务。`rag/keyword_backends.py` 定义了

| 后端 | 状态 |
|---|---|
| `postgres_fts` | **已实现**（默认）。Postgres 内置 `tsvector` + `ts_rank_cd` |
| `paradedb_bm25` | **刻意不实现**。`build_query()` 直接抛 `NotImplementedError` 并写明原因 |

**为什么不实现 BM25**（两条，都是实测出来的）：

1. 本地 Postgres 装不上 `pg_search` 扩展 —— 写了也验证不了，
   写出来的代码是**没跑过的代码**。
2. 2B 评测测出当前瓶颈是**中文同义表述召不回**（关键词路 0 块命中），
   换 BM25 改善不了这个 —— BM25 解决的也是"字面不匹配"，
   而"一周"vs"每周"是**分词/同义**问题，不是打分问题。

`NotImplementedError` 的消息里写死了这两条原因 ——
**静默退化最坏**：用户以为在测 BM25，实际跑的是 FTS，数字对不上还找不到原因。

配置项 `settings.keyword_backend`（默认 `postgres_fts`）。
配了**不存在的名字**，或配了**还没实现的后端**（`paradedb_bm25`），
都会**静默退回** `postgres_fts` —— 检索链挂掉比"用默认跑"糟糕得多。

> **这里踩过一个坑**：最初 `get_backend()` 只按名字查注册表，
> 配了 `paradedb_bm25` 就把那个骨架交出去，而它的 `build_query` 抛
> `NotImplementedError` —— 结果是**每一次**检索都炸，整条检索链挂掉。
> 修法：协议上加 `implemented` 标志，`get_backend` 跳过未实现的，
> `available_backends()` 只列真正能用的。

退化是**可见的**：`/health` 同时报 `keyword_backend`（实际生效的）和
`keyword_backend_configured`（配置里写的），两者不一致就是配错了。
