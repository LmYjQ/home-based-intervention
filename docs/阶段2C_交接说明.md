|---|---|---|

| `render_answer` | 输出家长可读回答 | `final_answer` |

### 2.2 路由

```python
def route_after_evidence_gate(state: CoachState) -> str:
    d = state["evidence_decision"]
    if d["high_risk"]:        return "professional_support"
    if d["needs_followup"]:   return "followup"
    if d["decision"] == "recommend": return "recommend"
    return "limited_answer"
```

### 2.3 引用校验（**必须实现**，计划 §9.3 验收点）

逐条检查 `RecommendationCard.source_citations` 里的每一条：

1. `citation.source_id` 必须能在当前 `EvidenceBundle` 的 `evidence_id` 里找到
   —— 找不到就是**编造引用**
2. 章节和页码必须与对应的 `EvidenceItem` 一致
3. `application_label == "source_summary"` 时必须至少有一条引用

任何一条失败：**带错误信息重试一次**；仍失败则**丢弃该卡**，
降级为 `limited_answer`，并在 trace 里记 `citation_validation_failed`。

> **字段语义的坑**：计划 §5.5 说"每一条 `source_citations` 必须能在
> 当前 `EvidenceBundle` 中找到对应 `evidence_id`"，而校验清单写的是
> "`citation.source_id` 是否存在"。
> **实现约定：`SourceCitation.source_id` 里放的是 `evidence_id`（chunk 的 UUID）**，
> 不是 `knowledge_sources.source_id`（`guideline2026`）。
> 这样校验才能精确到"页码对不对得上"。
> 写 prompt 时要明确告诉模型这一点，否则它会填 `guideline2026`。

### 2.4 安全审查（规则优先，LLM 复核为辅）

检查项：诊断性结论 / 强迫眼神接触或压制拒绝 / 缺停止条件 / 大段原文 /
把 AI 转化说成指南原话。结果三选一（详见计划 §9.3）。

**中文规则已经写好了**（`rdi_agent/graph/safety.py`，24 个用例覆盖）：
诊断性措辞（"确诊了""是自闭症"）、惩罚建议（"罚站""关小黑屋"）、
误引指南（"指南原话"）。规则是**句级**匹配而不是整卡匹配 ——
指南自己就写"挑战性行为""自闭症儿童"，整卡匹配会把指南原话也拦掉。

### 2.5 生成约束（写进 prompt）

1. 只能用 `EvidenceBundle` 里的内容作为专业依据
2. 每条专业主张必须对应一个 `evidence_id`
3. 明确区分"指南依据摘要"和"应用转化建议"
4. 每张卡必须包含观察指标和停止条件
5. **证据不足时不得补写书中观点**
6. 不输出诊断、不强迫孩子、不把单次行为标签化
7. 生成 2–3 个候选，明确推荐一个并说明理由

## 3. 开工前要决定的几件事

### 3.1 `retrieval.py` 怎么拆

现在 `retrieve()` 是一个大函数（改写 → 双路 → RRF → 重排 → 父块扩展 → 证据）。

图里要拆成 `retrieve_knowledge` 和 `rerank_and_expand` 两个节点，
**建议拆成三个可单测的公共函数**：

```python
recall_candidates(queries, candidate_k, use_vector) -> (vector_cands, fts_cands, merged)
build_evidence_bundle(candidates, queries, ...) -> EvidenceBundle
```

`retrieve()` 保持为"三步串起来"的便捷入口（评测脚本在用，别删）。

**注意 `retrieval_candidates` 放什么**：计划 §4.2 说
"原文片段只放 `evidence_id` 或摘要，避免 State 膨胀和日志泄露儿童信息"。
所以 `state["retrieval_candidates"]` 应该是**精简的**候选列表
（chunk_id + score + 页码 + 一小段摘要），不是完整候选对象。

### 3.2 `rewrite_query` 节点的查询怎么来

`query_rewrite.rewrite_query()` 现在接受**一个字符串**。
但图的输入是 `case_summary`（结构化）。

`CaseSummary` 的字段：`observed_facts` / `parent_goals` / `context` /
`already_tried` / `missing_information` / `retrieval_concepts` / `risk_signals`。

**待定**：怎么从这些字段拼出检索查询？
建议：优先用 `retrieval_concepts`（已经是抽取出的概念线索），
不够时用 `observed_facts` 拼。**但要注意计划 §5.4 的约束**：

> 查询改写只能使用**已确认事实**，不能把待验证假设写进检索词，
> 否则会把假设当成事实检索。

`retrieval_concepts` 是"线索"，不是事实 —— 这个边界要想清楚。
（`CaseSummary` 没有区分"已确认"和"待验证"的字段，可能需要看
`tentative_interpretations` 之类的结构，或者在 prompt 层面约束。）

### 3.3 `summary_zh` 要不要在 2C 做

计划 §9.2 里我误勾了这项（已更正为未完成）。计划 §5.3 的策略是
"只为进入证据包的 6–8 块生成中文摘要，写入 `knowledge_chunks.summary_zh` 缓存"。

**注意版权边界**：摘要是**转述**，不是原文引用，所以可以生成并给家长看；
但 `may_quote_to_user` 恒为 `False`（这本书授权未核实）。

`summary_zh` 的缓存失效：重新入库后块 id 变了 → 摘要要重算。
`KnowledgeChunk` 已经有 `embedding_version` 字段，可以当版本号用。

### 3.4 证据门控怎么判

计划 §5.5 给了五条路径：

| 条件 | `evidence_status` | 路由 |
|---|---|---|
| 有直接相关且定位准确的证据 | `direct` | `recommend` |
| 只有间接相关证据 | `indirect` | `limited_answer` |
| 检索结果互相矛盾 | `conflicting` | `limited_answer` |
| 没有可靠证据 | `none` | `limited_answer` |
| 缺失信息会改变建议 | `none/indirect` + `needs_followup` | `followup` |

**建议规则优先**（能纯规则判的不调 LLM）：
- 证据包为空 → `none` / `limited_answer`
- 有证据但 `relevance_reason` 全是"仅向量召回"、术语桥接为 0、且重排降级
  → 可能是 `indirect`
- 其余交给 LLM 判 `direct` / `indirect` / `conflicting`

**但 2B 量出过一个大问题**（`evals/REPORT_v1.md` §5.1）：
**无关问题也会召回 5 条证据**（硬凑率 100%）。所以
"证据包非空"**不能**直接当成"有证据"——
门控如果只判空不判质量，2C 就会把噪声当依据给家长。

> **这一条在中文指南这一版已经修掉了**（`evals/REPORT_v3.md` §2）：
> 硬凑率 **0%**（3 条无关题一条都没硬凑）。做法是给向量路加相似度下限
> （`MAX_VECTOR_DISTANCE = 0.52`）—— 中文 bge-m3 上相关查询最近邻距离
> 0.2876–0.4691、无关查询 0.5675–0.6071，0.52 是分界。
> **但门控仍然要判质量，不能只判空** —— 阈值是标定出来的，不是保证。

## 4.5 阶段 1 遗留 bug：API 层不会恢复 LangGraph 中断（已修）

**这是接手前必须知道的一件事** —— 2C 改 `rdi_agent/api/conversations.py` 时，
图的改法要跟它对齐。

### 症状

`make demo` 走不完闭环：追问没完没了，永远到不了方案选择；
就算手动选方案，`trial_id` 也是 `null`。

### 根因

`send_message` / `select_plan` 用的是**普通 dict** 调 `graph.ainvoke(...)`：

```python
await graph.ainvoke({"user_message": msg, ...}, config=config)   # ❌
```

LangGraph 里，**普通 dict 不会恢复 `interrupt()`**，它会让图**从 START 重跑一整条链**。
后果有三个：

1. `await_user_answer` 节点永远跑不完 → 每轮都是一个新开的中断
2. `followup_rounds` 永远是 `None` → `MAX_FOLLOWUP_ROUNDS = 3` 那个兜底**形同虚设**，
   模型可以无限追问
3. `present_plans` 的中断没被恢复 → 它后面的 `commit_plan_selection` 根本不执行
   → **trial 建不出来**

### 修法

按"当前 thread 停在哪个中断上"分流，停下时用 `Command(resume=...)`：

```python
pending = await _pending_interrupt(config)     # 读 aget_state().tasks 里的 interrupts

if pending and pending.get("kind") == "followup":
    result = await graph.ainvoke(
        Command(resume=req.message, update={"turn_id": turn_id}), config=config)
else:
    result = await graph.ainvoke({...普通 state...}, config=config)   # 新开一轮
```

`select_plan` 同理，用 `Command(resume={"plan_id": ...})` 恢复方案选择中断。

> `Command(update=...)` 里的 `turn_id` 是必要的：恢复时节点会重跑，
> 不显式带上就会用旧的 turn_id，幂等判断会串。

### 为什么之前没被测出来

`tests/test_graph_flow.py` 是**直接调图**、用 `Command(resume=...)` 恢复的 ——
它测的是图，测不到 API 层。**图是对的，API 是错的**，所以全部单测都绿。

新增 `tests/test_api_conversation_flow.py`：从 API 入口走一遍，
断言 `followup_rounds` 真的递增、第 3 轮兜底真的强制收手、`trial` 真的落库。
（改了 API 的中断恢复方式，**必须**跑这个文件。）

### 对 2C 的影响

2C 要在图里加 `evidence_gate` 等节点，**接口层也要跟着改**：
新增的 `safety_review` / `render_answer` 如果也要中断，
`rdi_agent/api/conversations.py` 的 `_pending_interrupt` 分流要一起扩。

**目的**：让人能在浏览器里把整条闭环走一遍，不用写脚本就能验收 2C。

| | |

**这个测试台特意做成"调试工具"而不是产品界面**：

**MANUAL_TEST.md 覆盖的 2C 验收点**：证据面板的字段（章节/页码/摘要/审核状态/
`may_quote_to_user` 恒 false）、方案卡的引用能不能对上 `evidence_id`、
`source_summary` 有没有引用、停止条件非空、出现诊断性结论就记 bug。

**前端已经改成中文标签**（`PlanCard.vue`）：`source_summary` → 指南依据，
`ai_adaptation` → 应用转化，`expert_reviewed` → 专业审核；
`source_type === 'guideline'` 显示"指南"。家长需要看懂的是
"这条是指南里说的"还是"这是我们根据指南做的应用转化" —— 这两件事必须分得清。

### 4.6.1 顺带修掉的一个 500：`recommended` 漏写

**症状**：生成建议卡那步 500，日志是

```
LLMError: build_recommendation 连续 3 次 schema 不合规：plans(value_error)
```

**根因**：`RecommendationCard.recommended` 在 pydantic 上有默认值 `False`，
所以它**不在** json_schema 的 `required` 列表里 —— 结构化输出允许模型整张卡
都不写这个字段。漏写之后三张卡全是 `False`，
`RecommendationSet` 的「必须恰好一张卡 recommended=True」校验就抛错。
实测**大约三次里撞上一次**（第一次跑完整流程就撞上了）。

**修法**（两层）：

1. `RecommendationCard` 加 `json_schema_extra` 钩子，把 `recommended`
   塞进 json_schema 的 `required` —— **从协议层堵住漏写**。
   pydantic 侧保留默认值，只让**模型**必须显式表态，
   代码构造这张卡时不用每次都写。
2. `build_recommendation` 节点 catch `LLMError`，降级为 `limited_answer`
   而不是让整个请求 500。计划 §9.3 的原意是「生成不出来就给有限回答」，
   不是「整个请求挂掉」。家长拿到一句有限回答，比拿到一个 500 强。

> **没有动 `RecommendationSet` 的严格校验**。
> `tests/test_conversation_schemas.py` 里
> `test_recommendation_set_rejects_zero_recommended` 编码的是有意的契约
> （"一张都不推荐等于把活推回去"），放宽它等于把这个设计意图扔了。
> 新增的回归测试 `test_recommended_is_required_in_json_schema` 断言的是
> **json_schema 的 required 列表**里有这个字段。

## 5. 硬约束（别踩）
