# 前端手动测试脚本（frontend_rdi/）

**照着点，每一步都写了「输入什么 → 预期看到什么」。预期不对就是回归，记下来。**

写于 2026-10-22。这个测试台是给**阶段 2C**（检索 + 证据门控 + 引用校验）用的，
目标是让人能在浏览器里把整条闭环走一遍，不用写脚本。

> 跟旧 `frontend/` 的区别：旧的那套是 `asd_agent/` 遗留的，已冻结，**不要动**。
> 新的在 `frontend_rdi/`，打的是 `rdi_agent` 的 API（8000 端口）。

---

## ⚠️ 2026-10-26 界面变了：依据从"右侧面板"挪进"卡片里"

这一版把**引用下沉到片段**，同时**取消了右侧的证据面板**。

| 以前 | 现在 |
|---|---|
| 右侧一个证据列表（章节、页码、摘要、「已引用」徽章） | 依据在**卡片自己的下方**，默认折叠，点「这次的依据（N 条）」展开 |
| 引用挂在整张卡上（`source_citations`） | 说明被拆成**片段**，每段后面挂一个编号（`[1]`、`[2]`…），点编号直接跳到对应那一条 |
| 卡片上写「见右侧证据第 N 条」 | 卡片上的编号就是依据的编号，**点一下就展开并高亮** |

**为什么这么改**：卡级引用回答不了"**这句话**依据的是哪一条"；
而同一个东西在右边列一遍、左边再列一遍，家长不知道该看哪边。

**老的验收点怎么对应**：

- "右侧证据面板 N 条" → 展开卡上的「这次的依据」，看有几条
- "「已引用」徽章" → 依据列表里**被卡片引用到**的那些（也就是卡上有编号的那些）
- "见右侧证据第 N 条对得上吗" → 卡上的编号和依据列表的编号**本来就是同一个**
  （两边都由同一份 `evidence_ids` 顺序算出来）
- "展开右下角 evidence_decision 原始 JSON" → 状态徽章挪到了**候选方案区块的头部**
  （「有直接依据 / 只有间接参考 / 没找到足够依据 / 需要专业支持」）

## 第 3 步：说第一句

在输入框填：

```
孩子4岁，最近不愿意去幼儿园，早上出门就哭。
```

回车（或点「发送」）。

**预期**：
- 消息区出现一条蓝色「家长」气泡
- **消息区下方出现进度条**，逐条列出「正在理解你说的情况」→
  「正在判断信息够不够」→「正在准备要问你的问题」→「问题已经好了，等你回答」。
  最后一条有个会呼吸的蓝点（当前步）。走完大约 10–30 秒
- 进度条消失后，出现「教练」气泡，内容是「（N 个问题）」
- 顶栏状态徽章变成 `追问中`（黄）
- 黄色提示条：**「图停在 await_user_answer 中断上。家长答完这一轮才会继续往下走。」**
- 左侧出现「要回答的问题」**作答卡片**（`FollowupStepper`）：
  - 顶部是「第 1 / N 题」和「已答 0 / N」两个徽章
  - 下面一排**圆点进度条**，一题一个点，点过的可以点着跳题
  - 当前题的问题文本 + 括号里的「为什么问这个」
  - 下面几个**点选选项**（LLM 按这题内容生成的，2–4 个）
  - 再下面一个「或者自己写」的文本框
  - 底部是「← 上一题」「下一题 →」，最后一题是「提交回答」
- 还没有「候选方案」区块（**追问阶段本来就不检索** —— 检索在信息够之后才跑）

**不对的话**：
- 报 500 → 看后端日志
- 一直转圈 → `/health` 的 `llm_ok` 是不是 false
- **进度条一直不出现** → 浏览器 Network 里看 `/messages/stream` 是不是
  `text/event-stream`。不是的话说明走了同步端点（前端回退逻辑不对）
- **进度条卡在某一步不动** → 记下卡在哪一步，对后端日志里那个 stage 查
- 问的问题跟场景完全不搭 → 记下来，这是 prompt 的问题
- **选项一个都没有** → 看原始响应里 `questions[].options` 是不是空数组。
  空数组是合法形态（模型想不出好选项），但**所有题都空**就说明
  `options` 没进 json_schema 的 required，模型整题都省了这个字段

## 第 4 步：答完这一轮追问

> **最多问两轮。** 后端 `MAX_FOLLOWUP_ROUNDS = 2` —— 家长答完第一轮后，
> 系统会判断信息够不够：够就直接出方案，不够才问第二轮。
> 第二轮答完强制出方案，不会有第三轮。

### 4.1 一轮之内怎么答

所有题**一起出来**，但一次只显示一题，左右切换：

| 操作 | 预期 |
|---|---|
| 点一个选项 | 按钮高亮变蓝，对应的圆点打勾 |
| 在文本框里打字 | **选项立刻变灰失效** —— 写了字就只提交字（Claude Code 的规矩） |
| 点「下一题 →」 | 换到下一题，**上一题的回答保留**（草稿也在） |
| 点「上一题」或圆点 | 换回上一题，之前选的选项/写的字都还在 |
| 答完最后一题 | 「提交回答」按钮才变亮；没答完时灰着，右边提示「还有 N 题没答」 |

点选项后圆点上会出现 ✓。**一轮答完只提交一次** —— 提交后请求体是：

```json
{"message": "", "answers": [{"question": "...", "answer": "..."}, ...]}
```

每条都带**原问题**，后端拼成给图看的文本时不会把多题串味。

### 4.2 提交这一轮之后

提交后，消息区多一条「家长」气泡（内容是「问题 + 答案」的组合）
+ 一条「教练」气泡。

**预期**：
- 提交后消息区下方出现进度条，走完整条检索链：
  「正在整理检索词」→「正在检索指南」→「正在筛选最相关的段落」
  →「正在检查依据够不够」→「正在整理建议」→「正在做安全检查」
  →「正在整理最终回复」→「正在把方案交给你看」

  > 看到「正在检索指南」就说明这一轮走完了，检索链真的跑了。
- **答完之后**，状态徽章从 `追问中` 变成 `待选方案`（蓝）
- 黄色提示条换成：**「图停在 present_plans 中断上 —— 必须调 select-plan 才会执行 commit_plan_selection，trial 才落库。」**
- 「候选方案」区块头部出现**依据状态徽章**（有直接依据 / 只有间接参考 / 没找到足够依据 / 需要专业支持）
- 左侧出现「候选方案」区块，2–3 张卡
- 卡上「说明」里的段落后面带着**编号角标**（`[1]`、`[2]`…）——
  没有编号的段落是"我们的应用转化"，有编号的才是"指南里说的"

> **答完还在追问就是 bug。** 最多两轮
> （`MAX_FOLLOWUP_ROUNDS = 2`）。如果还在追问，看后端日志里的 `followup_rounds` ——
> 它应该已经到 2 了。
>
> **第二轮必须问出新的东西。** 后端把「问过的问题 + 家长的答案」
> 成对透传给模型（`asked_qa_pairs`），模型据此判断：
> - 家长**答了** → 这件事问完了。基于答案往下走，**不要再问**
>   （要补就另起新角度，比如家长答"换过老师"，
>   该问的是"换老师之后在园表现有没有变化"）。
> - 家长**没答上来** → 换角度问，问得更具体、能给选项，
>   但不换个说法重问原问题。
>
> **如果第二轮还是问了第一轮那个问题**（比如第一轮问
> "在园和在家表现有什么不同"，第二轮又问"孩子在幼儿园和在家的
> 表现具体有哪些不同"），就是 bug —— 记下两轮的原文，
> 看后端日志里 `asked_qa_pairs` 有没有带上答案。
>
> 信息不够也照样出方案 —— 建议卡里有 `uncertainty_notes`，
> 方案本身会标出哪里不确定，这比多问一轮有用。

### 4.3 中途刷新页面

刷新之后应该**原样接回来**：

- 顶栏还是「追问中」
- 作答卡片还在，题目和选项都在
- 消息区能看到之前的对话
- 进度条不显示（请求已经结束了，正常）
- 已答的进度（勾）会**丢**（草稿存在内存里，不落库）—— 这是有意的，
  免得把家长的半截答案当成正式回答

如果刷新后**发送按钮是灰的**，或者页面报 400：
说明 localStorage 里存的 conversation_id 后端不认（比如换了数据库）。
这时点「新建会话」就会清掉它重新开始。

## 第 5 步：核对卡上的依据

这一步是 2C 的核心验收点，**逐条对着看**。

依据现在在**卡片自己的下方**：点「这次的依据（N 条）」展开。

| 看什么 | 预期 |
|---|---|
| 条数 | 1–10 条。**0 条且状态是「待选方案」= 异常**（没有依据却出方案） |
| 章节 | `section_title` 不是空的 |
| 页码 | `PDF 第 232–232 页` 这种格式，数字合理 |
| 摘要 | 是**转述**不是大段原文 |
| 编号 | 每条前面有个编号（1、2、3…），和卡上段落后面的角标**对得上** |
| 支撑 | 卡级引用会写「支撑：…」——哪句话是靠这一条撑的 |
| ⚠ 标记 | 「没在本次证据里找到这一条」= 引用挂了，记 bug |

**重点核对**：
1. **摘要里有没有大段原文？** 有 = 版权闸门漏了，记 bug
2. **卡上段落后面的编号，点开能跳到对应那一条吗？** 跳不过去 / 编号对不上就是 bug
3. **有没有段落是没有编号的？** 有 = 那是"我们的应用转化"，这是对的；
   但如果它讲的是指南里的专业主张，就是 bug
4. **召回的内容跟场景相关吗？** 不相关就是 2B 报告 §5.1 那个「硬凑率 100%」的问题，
   现在还在

依据状态看**候选方案区块头部**的徽章，**预期**：

| 徽章 | 什么时候出现 |
|---|---|
| 有直接依据 | 门控判成 `direct` |
| 只有间接参考 | 判成 `indirect` |
| 证据互相矛盾 | 判成 `conflicting` |
| 没找到足够依据 | 判成 `none` |
| 需要专业支持 | 判成 `risk` |

## 第 6 步：核对方案卡

对每张卡看：

| 看什么 | 预期 |
|---|---|
| ★ 推荐 | **恰好一张**有 |
| `application_label` | `book_summary` 或 `ai_adaptation`。**出现 `expert_reviewed` = bug**（这阶段没实现） |
| 依据事实 | 都来自家长说过的话，**不能有诊断性结论** |
| 可能解释 | 措辞是「可能 / 尚未证实」 |
| 家长可以做的事 | 有 `action` 和 `context` |
| 怎么算有效果 | **非空**（schema 强制） |
| 什么时候该停 | **非空**（schema 强制） |
| 引用 | 展开「这次的依据」能看到：章节名 + 页码 + 这段的大意 + 支撑的是哪句话 |

**引用怎么显示的（这一版改成片段级）**：

说明被拆成 `explanation_parts`，**每段带自己的 `evidence_ids`**，
段后面挂一个编号（`[1]`、`[2]`…）。动作也带 `evidence_ids`，
所以"这一步的依据是哪一段"也是确定的。

- 编号按「说明段 → 动作 → 卡级引用」的顺序算，**卡上显示的编号和
  依据列表的编号是同一个**（两边都由同一份 id 顺序算出来）
- 卡上显示的**章节和页码取自证据**（不是取引用上模型填的那些 ——
  模型经常填 `null`），页码才是准的
- 没有编号的段落 = 我们的应用转化，不是指南原话
- 引用在证据里找不到时，卡上会明写「⚠ 没在本次证据里找到这一条」

**最关键的一条**：标了 `source_summary` 的卡，
它的每一条 `source_citations.source_id` 都必须能在本次证据里找到对应的 `evidence_id`，
而且**页码要对得上**。对不上 = 编造引用 = 这张卡应该被丢掉。

**片段级多出来的一条**：段落里提到的指南术语（"消退""正强化"这类），
必须真的出现在**它挂的那条**证据里。挂错证据和编造一样会被丢掉。

> 引用校验是硬闸（计划 §9.3）：对不上会带错误信息重试一次，
> 仍失败就丢卡降级成「有限回答」。所以**正常情况下你看不到引用对不上的卡** ——
> 看到了就是 bug。

**不该出现的内容**（看到了立刻记 bug）：
- 诊断性结论（「这是自闭症」「这是分离焦虑障碍」）
- 强迫眼神接触、压制孩子的拒绝（「必须让她看着你的眼睛」）
- 把 AI 转化说成原书原话
- 缺停止条件

## 第 7 步：选方案

点想选的那张卡的「选这张」。

**预期**：
- 状态徽章变成 `已完成`（绿）
- 候选方案区标题右边出现「已选 plan_x」
- 「教练回复」区块出现一段话
- **出现「记录这轮尝试的反馈」表单**（说明 `trial_id` 落库了）

> **不选方案的话，trial 不会落库** —— 图停在 `present_plans` 中断上，

## 第 8 步：录反馈

填：
- 「执行情况」：`在门口只坚持了告别就离开了`
- 「孩子的反应 / 行为」：`蹲下`
- 「家长的观察」：`今天没有哭`（一行一条）
- 「执行困难」：`老人帮忙送，流程被压缩`（一行一条）
- 「这轮执行到哪一步」：做了 / 做了但中途停了 / 没做

点「提交反馈」。

**预期**：
- 出现「反馈结果」区块，头部有**决策徽章**：
  `继续当前方案` / `根据指南调整这一步` / `还需要补充信息` / `先停一停`
- 实际执行 / 观察到的变化 / 执行障碍 / 与方案的关系 / 置信说明 / 下一次 都有内容
- **「与方案的关系」不能是「方案有效」这种结论** ——
  反馈契约刻意只描述观察到的关系，不下因果结论。看到了就是 bug。
- 如果选了「做了但中途停了」，后端 `trials.status` 应该是 `stopped`，
  不是 `attempted`（可以在调试面板或直接查库确认）。

**分支 A —— 还需要补充信息**：
- 状态徽章是 `反馈追问中`
- 表单换成追问界面（和聊天追问同一个 Stepper），问题不超过 3 个
- 答完提交后，状态变成 `已完成`

**分支 B —— 根据指南调整这一步**：
- 「反馈结果」里出现「根据指南的调整」：headline / 调整动作 / 留意 / 停止条件
- 「这次的依据」有编号条目（章节 + PDF 页码 + 摘要）
- **不会出现新的方案卡**，也不会新建 trial —— 这是反馈迭代，
  调整的是正在执行的那一条

**分支 C —— 先停一停**：
- 决策徽章是红色「先停一停」，回复里明确说不用勉强继续
- 不出现新方案卡

> 重试同一个反馈（同一个 `turn_id`）不会再跑一遍模型：
> 后端看到 `feedbacks.completed_at` 直接返回缓存。

## 第 8.5 步：情况有变 → 重新出一版方案（阶段 4.5）

反馈结果卡片最下面有「情况有变？重新出一版方案」：
输入框填 `家里没人帮忙接送，只能晚上做`，点「重新生成方案」。

**预期**：
- 状态变成「待选方案」，「候选方案」头部出现 `第 2 版`
- 新卡卡号是 `r2_plan_1` / `r2_plan_2`…（**不能还是 `plan_1`**，
  撞号会让新卡根本落不进库）
- 第 1 版那一组还在，标成「已归档」，灰显、**不能选**
- **没有被重新提问**，也没有重新检索 —— 这次只重跑"生成卡 → 安全审查"
- 「上一次接口的原始响应」里 `reused` 有 `evidence_bundle` / `evidence_gate`，
  `plan_version` 是 `2`；新卡的证据包 id 和上一版相同

选一张第 2 版卡：
- 建的是**新的一次尝试**（trial 变了，下面是新的反馈表单）
- 第 1 版的 trial 和它的反馈仍在历史里，没有删
- 刷新页面后，第 1 版仍显示为「已归档」，第 2 版是「当前版本」

**分支 —— 补充的是风险信号**：
再点一次「重新生成方案」，填 `孩子最近开始打人，还会推倒小朋友`。
- 状态变成「建议转专业支持」，**不出新卡**
- 回复里请家长尽快找专业人员面对面评估，并说明什么情况要立刻就医
- 不会因此新建 trial

### 10.1 场景一：直接证据 → 出方案卡

- 还没有「候选方案」区块（追问阶段本来就不检索）

答完这一轮追问（题目是模型出的，**用自己的话答就行**，

## 第 11 步：长期记忆（阶段 3 验收）

右栏顶部多了一个「长期记忆」面板。这一节验的是计划 §10.7 的七条，
**重点不是"记没记住"，而是"记错了会不会出大事"**。

每条都先看右栏面板，再看左栏回答。

### 11.1 第一轮：会记下什么

1. 点「新建会话」
2. 发：`孩子今年五岁了，早上出门一直抱着我的腿，到幼儿园门口就哭。`
3. 等本轮跑完

**预期**：
- 面板出现「事实」分组，内容类似「孩子 5 岁」
- 每条下面有 `原话：孩子今年五岁了` —— **必须是家长自己说的字**，
  不是模型改写过的
- 模型猜的东西（比如"可能在分离时紧张"）出现在「假设」分组，
  而且标着 **待验证** / **系统推测**，**不能**出现在「事实」里

> 模型推断进了事实分组 = 严重 bug（计划 §10.3 的硬规则）。

### 11.2 同一孩子新会话：第二轮还记不记得

1. 点「同一孩子新会话」（不是「新建会话」）
2. 发：`今天在幼儿园门口哭得比昨天厉害。`
3. 如果它追问，注意题目

**预期**：
- 面板里的「孩子 5 岁」还在
- **追问里不会再问"孩子几岁"** —— 已经知道的会进 prompt 的 `known_facts`，
  prompt 里写死了"已知的不要再问"
- 右下「上一次接口的原始响应」里的 `memory` 字段有内容

> 追问又问了一遍年龄 = 记忆没接进 prompt，验收第 1 条不过。

### 11.3 纠正：改了之后还用不用旧值

1. 在面板里找到「孩子 5 岁」，点「纠正」，改成 `孩子 6 岁`，保存
2. 发起新一轮对话：`他最近在幼儿园怎么样才能不哭？`
3. 看右栏原始响应里的 `memory` / 看回答里的年龄

**预期**：
- 面板里只剩「孩子 6 岁」；**刷新页面也只剩新的**
- 回答和 `case_summary` 里**不能再出现 5 岁**
- 数据库里旧的那条还在（`status=superseded`），审计没丢

> 回答里还提 5 岁 = 验收第 2 条不过。

### 11.4 确认与删除

- **确认**：如果面板里有「待确认」的条目，点「确认」，状态变成「已确认」
- **删除**：随便删一条，会弹确认框；删完之后刷新页面，**它不能回来**
- **重复点删除**不该报错（软删是幂等的）

### 11.5 反例削弱假设（可选，需要跑两轮）

1. 造一条假设：跟系统说 `他可能是一和妈妈分开就特别紧张吧。`
2. 等面板出现「假设」且状态是「待验证」
3. 再说一句反例：`今天出门他主动跟我挥手说再见了。`
4. 看面板里那条假设

**预期**：状态变成 **被削弱**，并且出现「有 1 条反例」的标记。

> 反例被静默丢掉 / 假设纹丝不动 = 验收第 7 条不过。

### 11.6 收尾检查

| 要看的 | 在哪 |
|---|---|
| 每条记忆都有原话 | 面板每条的 `原话：...` |
| 事实 / 偏好 / 观察 / 假设 分开 | 面板分组 |
| 待确认的不进回答 | 看「上一次接口的原始响应」里 `memory.confirmed_facts` 不含待确认条目 |
| 尝试是只读的 | 「尝试」分组没有确认/纠正/删除按钮 |
| 审计有记录 | `select * from memory_events order by created_at desc limit 20;` |

## 附录 B：接口一览

前端调的全是 `rdi_agent` 的接口，文档在 `/docs`（FastAPI 自动生成）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 逐项自检 |
| POST | `/api/conversations` | 建会话 |
| POST | `/api/conversations/{id}/messages/stream` | **发消息（前端现在走这个）**，SSE 推进度。**回答追问时带 `answers`**（见 §4.1） |
| POST | `/api/conversations/{id}/messages` | 发消息（同步版，结果一样）。手测脚本、curl 用这个 |
| POST | `/api/conversations/{id}/select-plan` | 恢复选方案中断 |
| GET | `/api/conversations/{id}` | 查会话状态 |
| GET | `/api/plans/{plan_id}` | 方案卡全文 |
| POST | `/api/trials/{trial_id}/feedback` | 录反馈 |
| GET | `/api/children/{child_id}/memories` | 长期记忆列表（`family_id` 必填） |
| POST | `/api/children/{child_id}/memories/{memory_id}/confirm` | 确认待确认的记忆 |
| PATCH | `/api/children/{child_id}/memories/{memory_id}` | 纠正（新建 + 旧的作废） |
| POST | `/api/children/{child_id}/memories/{memory_id}/delete` | 软删除 |

`POST /api/conversations` 现在可以带 `child_id` —— 传了就用这个孩子开新会话，
长期记忆会跟过来（前端「同一孩子新会话」按钮就是这么调的）。

**流式端点（SSE）**：推的是**进度**，不是半截答案。

抽取类调用走 `json_schema` 严格约束解码，模型必须保证 JSON 语法合法才能吐 token，
中途吐出来是半截 JSON，家长看不懂。所以这条流解决的是「它卡在哪儿」，
不是「字一个字出来」。

事件格式（`text/event-stream`）：

| event | data | 含义 |
|---|---|---|
| `progress` | `{stage, label, kind, detail, attempt}` | 走到某一步了。`label` 是给家长看的中文 |
| `result` | 和 `/messages` 的 body **完全一样** | 跑完了 |
| `error` | `{message}` | 出错了 |

`progress` 的 `stage` 会随流程变化 —— **阶段数不是固定的**，
取决于图走到了哪：

| 你做的 | 走过的 stage |
|---|---|
| 发第一句 | `intake_parse` → `sufficiency` → `followup` → `await_answer` |
| 答完一轮追问 | `await_answer` → `intake_parse` → `sufficiency` → `rewrite_query` → `retrieve` → `rerank` → `evidence_gate` → `build_recommendation` → `safety_review` → `render` → `present_plans` |

> **只发第一句就只看到前四个** —— 因为图停在追问中断上了，
> 后面的检索链根本没跑。**答完一轮追问再看，才看得到完整的 11 个。**

> 走「有限回答」那一路时，`build_recommendation` 会换成 `build_limited_answer`。

**状态值**（前端按这五种渲染，不要自己发明）：

| status | 含义 | 前端表现 |
|---|---|---|
| `awaiting_followup` | 停在追问中断 | 等家长回答 |
| `awaiting_plan_selection` | 停在选方案中断 | 显示候选卡，要点「选这张」 |
| `limited_answer` | 证据不够，给了有限回答 | 没有候选卡 |
| `needs_professional_support` | 门控判成高风险 | 建议转专业支持 |
| `completed` | 本轮跑完 | 显示教练回复 |

## 附录 C：已知问题

### C.1 `recommended` 漏写导致 500（已修）

**症状**：生成建议卡那一步 500，日志里是

```
LLMError: build_recommendation 连续 3 次 schema 不合规：plans(value_error)
```

**根因**：`RecommendationCard.recommended` 有默认值 `False`，
所以 json_schema 的 required 列表里没有它 —— 模型漏写这个字段是常态
（实测三张卡全漏，约三次里撞上一次）。全漏 → 0 张 `recommended=True`
→ `RecommendationSet` 的校验器抛错 → 整轮生成 500。

**修法**：**不动 pydantic 侧的校验器**（"必须恰好一张 recommended"
这条硬规则要留着），改成在 `model_json_schema()` 上加钩子，
把 `recommended` 塞进 required 列表 —— 模型**必须显式表态**，
但代码构造这张卡时不用每次都写。

判据是 **json_schema 的 required 里有这个字段**，
不是「pydantic 拒绝构造」。

### C.2 `source_citations` 漏写导致整轮退化（已修）

**症状**：不报错，但家长答完三轮追问后**拿不到任何建议卡**，
只拿到一段没有出处的文字。日志里是

```
LLMError: build_recommendation 连续 3 次 schema 不合规：
plans.0(value_error); plans.1(value_error); plans.2(value_error)
```

**根因**：和 C.1 是同一类问题，但字段是 `source_citations`。
模型把 `application_label` 填成 `source_summary`（"这是指南里说的"），
却不给出任何引用 —— 因为 `source_citations` 有默认值 []，
不在 json_schema 的 required 里，结构化输出允许模型整张卡都不写它。

然后 `source_summary_needs_citation` 校验器抛错，
**三张卡一起废掉**，整轮退化成有限回答。

**修法**：同样加 json_schema 钩子，把 `source_citations` 塞进 required。
要求"字段必须出现"不等于"必须有引用" —— 空数组是合法答案，
对应"这张卡是应用转化，不是指南原文"。

**另一个相关的坑**：这种退化**原本会被报成 `completed`** ——
`evidence_decision` 说的是 `recommend`（证据是够的），
所以只看它就以为流程正常跑完了。现在 `_status_of` 也看 `answer_mode`，
走到有限回答这一路就报 `limited_answer`。

### C.3 答完还在追问

第 4 步如果答完这一轮还在追问，是 bug。
查后端日志里的 `followup_rounds` —— 它应该已经到 1。

**为什么会反复问同一个问题**（2026-10-25 修的 bug）：

`parse_parent_input` 把家长这一轮的回答交给模型抽成 `CaseSummary`，
但**实测模型会把整段问答丢掉** —— 家长答了"没有不愉快的经历"，
抽出来的 `observed_facts` 里还是只有开场白那句话。

答案一丢，下一轮模型就以为这件事**没问过**，于是换个说法再问一遍。

修法：答案走**两条路**。
`answers` 结构化（`[{question, answer}, ...]`）随恢复值进 state，
由 `parse_parent_input` **在代码层确定性地**并进 `observed_facts`，
不指望模型抽。模型的抽取只当补充来源。

### C.4 选项按钮点不动（已修）

**症状**：「要回答的问题」卡片里的选项按钮点不动，也不高亮。

**根因**：`:disabled="draft.trim()"`。Vue 对布尔属性用 `includeBooleanAttr`，
**空字符串 `''` 会被当成 true** —— `:disabled="''"` 渲染成 `disabled=""`，
按钮直接点不动。输入框明明是空的。

**修法**：转成真正的布尔值再绑（`hasDraft = computed(() => draft.value.trim().length > 0)`）。

### C.5 切题时上一题的回答丢了（已修）

**症状**：在第 1 题点了选项，切到第 2 题再切回来，
选项没高亮、进度条上的勾也没了。

**根因**：`go()` 里手动调了 `saveDraft`/`loadDraft`，
而 `watch(current)` 里**也调了一遍**。watch 触发时 `draft` 已经是新一题的内容了，
于是 `saveDraft(prev)` 存进去的是**新一题的输入框** —— 上一题刚选好的答案被空草稿覆盖。

**修法**：`go()` 里不再手动存/取，只改 `current.value`，由 watch 统一处理。

### C.6 刷新后发送按钮是灰的（已修）

**症状**：刷新页面后第一次填问题，发送按钮是灰的点不动，
必须点一次「新建会话」才能发。

**根因**：`conversationId` 只存在内存的 `ref` 里，刷新就没了，
而 `canSend` 要求有 conversation_id。

**修法**：存进 `localStorage`，刷新后用 GET 把会话接回来
（状态、消息、追问题都恢复）。存下来的 id 后端不认的话（比如换了数据库），
就清掉它回到「先新建会话」的状态，而不是卡在灰按钮上。

### C.7 证据可能不相关

2B 报告 §5.1 测出**硬凑率 100%**（问「红烧肉怎么做」也返回 5 条证据）。
这个问题 2C 还没修。所以第 5 步看到不相关的证据是**已知问题**，
不是这个测试台的问题 —— 但要记下来，它是 2C 的验收点之一。

### C.8 刷新后方案卡只剩标题（已修）

**症状**：刷新页面后，方案卡只剩下标题和标签，
**引用、家长可以做的事、观察指标全没了** —— 看起来像"引用被清空了"。

**根因**：`GET /api/conversations/{id}` 返回的 `plans` 只有
`plan_id` / `title` / `status` / `recommended` / `application_label`
五个字段，整张卡的内容（`plan_json`）没返回。
前端把这份摘要直接喂给 `PlanCard` 渲染，于是卡上只剩标题。

**修法**：`list_plans` 改成返回整张卡（`plan_json` 展开在顶层，
同时保留 `card` 字段）。另外停在选方案中断时，
`GET` 优先返回**中断里那份候选卡** —— 那才是"当时给家长看的那三张"。

### C.9 进度条不出现 / 阶段缺一段（已修）

**症状**：进度条一直不出现，或者卡在某个阶段不动。

**排查**：
- 浏览器 Network 里 `/messages/stream` 是不是 `text/event-stream`
- **阶段数不是固定的** —— 只发第一句就只看到前四个
  （图停在追问中断上了，检索链根本没跑）。
  要看完整的 11 个阶段，得**答完一轮追问**再看
- 某个阶段缺了 = 那个节点没打点。抽取类调用接在
  `llm.chat_json` 上自动打点；纯函数节点（`render_answer`、
  `rewrite_query`）要手动 `progress.emit(...)`

**注意别打两次**：同一个阶段既手动 `emit` 又走 `chat_json`，
就会推两条重复的事件。前端会按 stage 去重，但流里是脏的。

### C.10 进度条消失太快

进度条在请求结束后 1.2 秒消失。**这是有意的** ——
立刻消失的话家长根本来不及看最后一步。
