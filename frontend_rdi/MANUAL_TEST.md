# 前端手动测试脚本（frontend_rdi/）

**照着点，每一步都写了「输入什么 → 预期看到什么」。预期不对就是回归，记下来。**

写于 2026-10-22。这个测试台是给**阶段 2C**（检索 + 证据门控 + 引用校验）用的，
目标是让人能在浏览器里把整条闭环走一遍，不用写脚本。

> 跟旧 `frontend/` 的区别：旧的那套是 `asd_agent/` 遗留的，已冻结，**不要动**。
> 新的在 `frontend_rdi/`，打的是 `rdi_agent` 的 API（8000 端口）。

---

## 第 0 步：起环境

### 0.1 起 PG

```bash
make db-up
```

**预期**：`docker ps` 里 `rdi-db` 状态 `Up (healthy)`。
库是 1178 块已向量化的那本，没向量的话检索会走空。

### 0.2 起后端

```bash
make dev
```

**预期**：
```bash
curl -s localhost:8000/health | python -m json.tool
```
→ `"status": "ok"`，且 `llm.llm_ok` 是 `true`、`pgvector.ok` 是 `true`。

> `llm_ok` 是 false 就先别测 —— 每一轮都要调模型，
> key 不对的话前端会在「处理中」卡到超时。

### 0.3 起前端

```bash
make web-install     # 第一次
make web
```

**预期**：`http://localhost:5176/`。
（5173/5174 被旧 `frontend/` 占着，这套固定用 5176。）

### 0.4 后端不在 8000 端口？

改 `frontend_rdi/vite.config.js` 里的 `target`，改完 vite 会自动重启。

## 第 1 步：体检

打开页面，**预期**：

| 位置 | 预期 |
|---|---|
| 顶栏 | `后端 ok`（绿）、`LLM Qwen/... · live`（绿）、`PostgreSQL 16.15`、`rerank on` |
| 右上角 | 「刷新会话」是**灰的**（还没建会话） |
| 左侧 | 「还没开始。先「新建会话」…」 |
| 右侧 | 证据面板「0 条 · 本轮没有取到证据」 |

**不对的话**：先看 `/health` 的 body，页面右下角会显示原始 JSON。
`status` 不是 `ok` 时顶栏是红的，`llm_ok` false 说明 key 有问题。

---

## 第 2 步：建会话

1. 「孩子称呼」保持 `孩子`，「年龄段」填 `3-4岁`
2. 点「新建会话」

**预期**：
- 「会话」标题右边出现 `conversation_id`（形如 `uuid.uuid.uuid`）
- 「刷新会话」变成可点
- 消息区还是「还没开始…」

> `conversation_id` 是三段 UUID 拼的。**不是三段就说明 API 层出问题了**，
> 后端解析不出来会直接 400。

---

## 第 3 步：说第一句

在输入框填：

```
孩子4岁，最近不愿意去幼儿园，早上出门就哭。
```

回车（或点「发送」）。

**预期**：
- 消息区出现一条蓝色「家长」气泡
- 大约 10–30 秒后出现「教练」气泡，里面是 1–2 个**追问问题**
- 顶栏状态徽章变成 `追问中`（黄）
- 黄色提示条：**「图停在 await_user_answer 中断上。家长答完这一轮才会继续往下走。」**
- 左侧出现「要回答的问题」列表
- 输入框的标签变成「回答追问」，占位符变「Enter 直接提交」
- 右侧证据面板仍是「0 条」（**追问阶段本来就不该有证据** —— 检索在信息够之后才跑）

**不对的话**：
- 报 500 → 看后端日志
- 一直转圈 → `/health` 的 `llm_ok` 是不是 false
- 问的问题跟场景完全不搭 → 记下来，这是 prompt 的问题

---

## 第 4 步：答完三轮追问

点输入框下面「快捷填入演示答案」里的「第 1 条」「第 2 条」「第 3 条」，
每点一次等它返回再点下一个。

**预期**：
- 每答一次，消息区多一条「家长」气泡 + 一条「教练」气泡
- 追问问题**会变**（每轮问的不一样，这是正常的）
- **第 3 轮答完之后**，状态徽章从 `追问中` 变成 `待选方案`（蓝）
- 黄色提示条换成：**「图停在 present_plans 中断上 —— 必须调 select-plan 才会执行 commit_plan_selection，trial 才落库。」**
- 右侧证据面板出现**证据条**（几条到十几条不等）
- 左侧出现「候选方案」区块，2–3 张卡

> **追问超过 3 轮就是 bug。** 计划 §8.4 定了 `MAX_FOLLOWUP_ROUNDS = 3`，
> 第 3 轮之后强制收手出方案。如果还在追问，看后端日志里的 `followup_rounds`。

## 第 5 步：核对证据面板

这一步是 2C 的核心验收点，**逐条对着看**：

| 看什么 | 预期 |
|---|---|
| 条数 | 1–10 条。**0 条且状态是「待选方案」= 异常**（没有依据却出方案） |
| 章节 | `section_title` 不是空的 |
| 页码 | `p.232–232` 这种格式，数字合理 |
| 摘要 | 是**转述**不是大段原文 |
| 召回理由 | 有内容（向量相似 / 术语桥接 / 重排） |
| `review_status` | `unreviewed` 或 `reviewed`，**不能是空** |
| `may_quote_to_user` | **恒为 `false`**（这本书授权未核实，不给原文） |
| `evidence_id` | UUID 格式 |

**重点核对**：
1. **摘要里有没有大段原文？** 有 = 版权闸门漏了，记 bug
2. **`evidence_id` 和方案卡引用对得上吗？** 下一条会用到
3. **召回的内容跟场景相关吗？** 不相关就是 2B 报告 §5.1 那个「硬凑率 100%」的问题，
   现在还在

展开右下角的「evidence_decision 原始 JSON」，**预期**：

```json
{
  "evidence_status": "direct" | "indirect" | "conflicting" | "none",
  "can_support_personalized_advice": true | false,
  "missing_information": []
}
```

## 第 6 步：核对方案卡

对每张卡看：

| 看什么 | 预期 |
|---|---|
| ★ 推荐 | **恰好一张**有 |
| `application_label` | `book_summary` 或 `ai_adaptation`。**出现 `expert_reviewed` = bug**（这阶段没实现） |
| 依据事实 | 都来自家长说过的话，**不能有诊断性结论** |
| 可能解释 | 措辞是「可能 / 尚未证实」 |
| 家长可以做的事 | 有 `action` 和 `context` |
| 怎么算有效果 | **非空**（schema 强制） |
| 什么时候该停 | **非空**（schema 强制） |
| 引用 | `source_id` 是 UUID，**且能在右侧证据面板的 `evidence_id` 里找到** |

**最关键的一条**：标了 `book_summary` 的卡，
它的每一条 `source_citations.source_id` 都必须能在证据面板里找到对应的 `evidence_id`，
而且**页码要对得上**。对不上 = 编造引用 = 这张卡应该被丢掉。

> 引用校验是硬闸（计划 §9.3）：对不上会带错误信息重试一次，
> 仍失败就丢卡降级成「有限回答」。所以**正常情况下你看不到引用对不上的卡** ——
> 看到了就是 bug。

**不该出现的内容**（看到了立刻记 bug）：
- 诊断性结论（「这是自闭症」「这是分离焦虑障碍」）
- 强迫眼神接触、压制孩子的拒绝（「必须让她看着你的眼睛」）
- 把 AI 转化说成原书原话
- 缺停止条件

## 第 7 步：选方案

点想选的那张卡的「选这张」。

**预期**：
- 状态徽章变成 `已完成`（绿）
- 候选方案区标题右边出现「已选 plan_x」
- 「教练回复」区块出现一段话
- **出现「记录这轮尝试的反馈」表单**（说明 `trial_id` 落库了）

> **不选方案的话，trial 不会落库** —— 图停在 `present_plans` 中断上，
> 后面的 `commit_plan_selection` 根本不跑。表单出不来就是这里没走通。

## 第 8 步：录反馈

填：
- 「执行情况」：`在门口只坚持了告别就离开了`
- 「孩子的反应 / 行为」：`蹲下`
- 「家长的观察」：`今天没有哭`（一行一条）
- 「执行困难」：`老人帮忙送，流程被压缩`（一行一条）
- 「这轮真的做了吗」：做 → 做了

点「提交反馈」。

**预期**：
- 出现「反馈结果」区块
- 实际执行 / 观察到的变化 / 与方案的关系 / 置信说明 / 下一步 五项都有内容
- **「与方案的关系」不能是「方案有效」这种结论** ——
  反馈契约刻意只描述观察到的关系，不下因果结论。看到了就是 bug。

点右上角「刷新会话」。

**预期**：状态、证据、候选方案都还在，不会因为刷新丢东西。
`GET /api/conversations/{id}` 的 `status` 和页面上显示的一致。

- 它**不调 LLM**、**不检索**、**不落库**

- 所以它能证明「前端渲染逻辑对」，**不能证明「后端业务对」**

## 附录 B：接口一览

前端调的全是 `rdi_agent` 的接口，文档在 `/docs`（FastAPI 自动生成）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 逐项自检 |
| POST | `/api/conversations` | 建会话 |
| POST | `/api/conversations/{id}/messages` | 发消息（可能停在追问/选方案中断） |
| POST | `/api/conversations/{id}/select-plan` | 恢复选方案中断 |
| GET | `/api/conversations/{id}` | 查会话状态 |
| GET | `/api/plans/{plan_id}` | 方案卡全文 |
| POST | `/api/trials/{trial_id}/feedback` | 录反馈 |

**状态值**（前端按这五种渲染，不要自己发明）：

| status | 含义 | 前端表现 |
|---|---|---|
| `awaiting_followup` | 停在追问中断 | 等家长回答 |
| `awaiting_plan_selection` | 停在选方案中断 | 显示候选卡，要点「选这张」 |
| `limited_answer` | 证据不够，给了有限回答 | 没有候选卡 |
| `needs_professional_support` | 门控判成高风险 | 建议转专业支持 |
| `completed` | 本轮跑完 | 显示教练回复 |

## 附录 C：已知问题

### C.1 `recommended` 漏写导致 500（已修）

**症状**：生成建议卡那一步 500，日志里是

```
LLMError: build_recommendation 连续 3 次 schema 不合规：plans(value_error)
```

**根因**：`RecommendationCard.recommended` 有默认值 `False`，
所以 json_schema 的 required 列表里没有它 —— 模型漏写这个字段是常态
（实测三张卡全漏，约三次里撞上一次）。全漏 → 0 张 `recommended=True`
→ `RecommendationSet` 的校验器抛错 → 整轮生成 500。

**修法**：把校验器从「报错」改成「归一」——
0 张就把第一张提上来，多张就只留第一张。
下游 `_generate_cards` 本来就有同样的补位逻辑，只是原来根本没机会跑到。

**怎么确认修好了**：连着跑几次「新建会话 → 答完三轮」，
不该再看到 `schema 不合规`。

### C.2 追问可能超过 3 轮

第 4 步如果答完第 3 轮还在追问，是 bug。
查后端日志里的 `followup_rounds` —— 它应该停在 3。

### C.3 证据可能不相关

2B 报告 §5.1 测出**硬凑率 100%**（问「红烧肉怎么做」也返回 5 条证据）。
这个问题 2C 还没修。所以第 5 步看到不相关的证据是**已知问题**，
不是这个测试台的问题 —— 但要记下来，它是 2C 的验收点之一。
